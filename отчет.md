# Отчёт по практической №1 — TPC-H Q18

Отчёт по результатам практической работы.

## 1. Вариант и масштаб

| Поле | Значение |
|---|---|
| ФИО | Чиркова Екатерина Николаевна |
| Группа | БИВТ-24-СП-1 |
| Вариант (запрос) | Q18 |
| Масштаб `sfN` | sf1 |
| Почему выбран такой масштаб | Для локального учебного запуска выбран `sf1`: объём можно обработать на одном компьютере, а в `lineitem` уже 6 млн строк. |

## 2. Поднятые сервисы — и почему именно они

| Сервис | Роль в стеке | Почему именно он |
|---|---|---|
| MinIO-compatible storage (`pgsty/minio`) | S3-совместимое объектное хранилище | Upstream-образ MinIO при запуске оказался недоступен; использована совместимая community-сборка на основе MinIO, чтобы выполнить ту же роль в локальном стеке |
| PostgreSQL | Метаданные Lakekeeper | Реляционная БД, поддерживаемая Lakekeeper |
| Lakekeeper | Iceberg REST Catalog | Каталог метаданных Iceberg |
| Trino | SQL-движок | Поддерживает TPC-H, Iceberg REST Catalog и S3 |
| Superset | BI | Подключается к Trino и показывает Bronze |

После `docker compose up -d --build` проверено через `docker compose ps -a`: запущены MinIO-совместимое хранилище, PostgreSQL, Lakekeeper, Trino и Superset. Миграции и инициализация Lakekeeper выполняются одноразовыми контейнерами и завершаются с кодом 0.

### Скрипты, которыми поднят стек

```bash
docker compose up -d
```

Команда запуска: `docker compose up -d --build`; конфигурация находится в `docker-compose.yml`. Superset собран с драйвером Trino из `superset/Dockerfile`.

## 3. Разбор запроса — какие данные нужны

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает |
|---|---|---|
| customer | все 8 полей TPC-H; в Silver используются `custkey`, `name` | Bronze сохраняет источник; Silver нормализует имя через `trim`, соединяет с заказами и выводит имя и ключ |

## 5. Тесты производительности

Сравнение выполнено на одинаковых таблицах TPC-H `customer`, `orders` и `lineitem` масштаба `sf1`. Для каждой комбинации формат/сжатие таблицы созданы командами из `sql/benchmark_tables.sql`; время записи рассчитано как сумма длительностей трёх CTAS-запросов по статистике Trino (`end - started`). Размер файлов получен из `sql/benchmark_sizes.sql` и переведён в десятичные МБ (1 МБ = 1 000 000 байт). Q18 из `sql/benchmark_q18.sql` запускался по одному разминочному и четыре измерительных раза на каждой комбинации; в таблице указана медиана четырёх измерений.

| Формат | Сжатие | Время записи трёх таблиц, с | Размер, МБ | Q18, медиана 4 запусков, с |
|---|---|---:|---:|---:|
| PARQUET | GZIP | 11,562 | 181,40 | 0,393 |
| PARQUET | ZSTD | 7,779 | 190,08 | 0,394 |
| ORC | GZIP | 8,106 | 189,12 | 0,415 |
| ORC | ZSTD | 6,663 | 202,81 | 0,397 |

В этой серии Parquet/GZIP дал наименьший размер (181,40 МБ), но записывался дольше остальных сочетаний Parquet. ORC/ZSTD записался быстрее всех (6,663 с), однако занял больше места (202,81 МБ). Медианы Q18 близки друг к другу (0,393–0,415 с), поэтому на `sf1` заметного преимущества по времени чтения в этих прогонах нет; небольшую разницу не стоит считать универсальной. Время записи измерено за один проход, поэтому оно сильнее зависит от текущего состояния локального Docker и хранилища.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1 Понять и объяснить

| Вопрос | Ответ |
|---|---|
| Зачем нужны большие данные и lakehouse? | Lakehouse хранит аналитические файлы в объектном хранилище и даёт работать с ними через SQL, сохраняя каталог и историю таблиц. Здесь файлы лежат в S3-совместимом хранилище, а метаданные Iceberg обслуживает Lakekeeper. |
| Пример schema evolution на Silver | В `iceberg.silver.enriched_orders` добавлена колонка `study_note VARCHAR`. `DESCRIBE` показал новый столбец; изменение прошло через метаданные Iceberg без пересоздания данных таблицы. |
| Пример восстановления из снимка (time travel) | Для `iceberg.gold.q18_top100` прочитан snapshot `3991630936445420239`: `SELECT count(*) FROM iceberg.gold.q18_top100 FOR VERSION AS OF 3991630936445420239;`. Результат — 57 строк. |

### 6.2 Подключить инструмент к lakehouse

| Инструмент | Почему выбран |
|---|---|
| Superset | BI-инструмент с SQL Lab для чтения Bronze через Trino |

Соединение `Trino Lakehouse` создано с URI `trino://admin@trino:8080/iceberg/bronze`. Подключение проверено из контейнера Superset запросом `SELECT count(*) FROM customer`; он вернул 150 000. Для показа в UI открой http://localhost:8088, войди как `admin` / `admin-local-only`, затем в SQL Lab выбери `Trino Lakehouse` и выполни тот же запрос.

## 7. Выводы

На масштабе `sf1` Q18 вернул 57 заказов, у которых общее количество товара больше 300. В Bronze сохранены исходные таблицы, Silver нормализует имена клиентов, отбирает крупные заказы и обогащает их сведениями из `customer` и `orders`, а Gold содержит итоговый результат. Бенчмарк показал компромисс: Parquet/GZIP дал меньший размер, ORC/ZSTD — самое быстрое время записи, а время Q18 было близким для всех вариантов. Для основных слоёв оставлен Parquet/ZSTD как сочетание умеренного размера и быстрой записи. Для `sf1` партиционирование не понадобилось. Дополнительно проверены изменение схемы Silver и чтение Gold из предыдущего snapshot.
